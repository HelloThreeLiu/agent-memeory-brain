【结论】**改后做**——架构决定（四层、双时间轴、daemon+shim、MCP 单边界、P1.5 时序）全部保住；本轮问题集中在规格文本与选型理由，两句规格话 + 一处选型修正即可冻结 schema 开工。

【致命问题】

**1. 9.3 的 B/C 路由在"同置信档"上重叠，最常见更新路径（observation→observation）归属悬空**
- 问题：B 的前置条件是"置信档 **≥** 旧条"（等号满足即通过），C 又把"**同置信档**"列为进仲裁的条件。obs→obs（0.85=0.85）、dec→dec（1.0=1.0）同时命中两条：按 C 读法，一切同类型新旧更替都开仲裁；按 B 读法，C 的"同置信档"永远不可达、是死文。两种读法必有一坏。而 obs→obs 恰是日常最常见路径（构建命令换了、依赖升了——"世界变了"不是"意见分歧"，valid_from 时序本来就是为区分它们而设）。
- 证据/反例：P1.5 第 3 周，B 档单角色使用，改了一次构建命令（fact_key=`build.cmd`）：旧 observation（0.85 档）→ 新 observation（0.85 档）。按 C 读法开 arbitration，而 P1.5 只暴露 remember/recall/expand 三工具、可视化在 P2/P3——队列只进不出，此后每轮注入永久携带"存在分歧，见 arb-xxx"。零 LLM 模式（硬约束 2）下规则抽取产出的几乎全是 observation，这不是边角场景。
- 建议改法：一句话定死路由——**同 assertion_type 的新旧对一律走 B**（按 valid_from 时序静默失效，含 obs→obs、dec→dec）；C 只收跨类型同档（如 rule 抽取的 observation 对 claim）与 valid_from 不可比两类。同步修 INV5 的"二者必居其一"，把 Route A 同角色情形（contradicts 边、不开仲裁）也纳入合法状态。

**2. 召回的有效性谓词未定义——重要 4 只修了 schema 半边，读路径仍是坑**
- 问题：8.1 宣布"有效性看 valid_to 不看 status"，12.2 给了"已失效"的视觉语义，但 9.4 的候选池规则只写了"archived 排除"。被取代条（status=active、valid_to 非空）在不在候选集？同一 fact_key 的历代版本折叠不折叠成"当前有效一条"？全文没有这句谓词。
- 证据/反例：`build.cmd` 换过三次后，top-k=5 可能被同一 key 的三条历史 + 一条当前占满，其中三条已失效——G1"同一事实不重复问第二遍"当场翻车，且注入内容互相矛盾，用户看到的是四条打架的构建命令。
- 建议改法：候选池谓词写进 9.4：**每个 fact_key 只取"有效区间覆盖当前时刻"的最新一条**；open-arbitration 对是唯一例外（双注入，与 9.3-C 一致）；历史条只经 expand 工具与时间视图访问——这本来就是双时间轴设计的卖点，缺的只是把它写成查询规则。

【重要但非致命】

**1. G6 的两个度量缺口：B 档没有反馈通道，"静默跳过率"不可测**
- 问题：P1.5 验收要求"≥20 次反馈"，但 B 档的注入是终端里的工具返回文本，16.2 承诺的"注入点反馈按钮"在 CLI 宿主没有物理形态。同时 16.2 把"静默跳过率"列为健康指标——沉默没有信号，方法论上无法区分"用了没说""读了没用""根本没看"。
- 证据/反例：第 4 天起用户对注入块连续无视：injection_log 全绿、feedback 表 0 行、负反馈率 0%——按 16.2 的指标体系系统完全健康，而信任实际已归零。这正是首轮"信任静默衰减"要防的事，防它的仪表本身是坏的。
- 建议改法：feedback 做成 P1.5 的第 4 个 MCP 工具（用户在对话里说"这条记错了"，模型代调 `feedback(id, wrong)`），或 CLI 斜杠命令——挤占声明：多一个工具挤掉"三工具"承诺，代价约半天。"静默跳过率"从指标表删除，换可测代理：负反馈率、recall 后续 turn 的 expand 调用率、注入条被引用数 / 注入条数。

**2. bge-m3 选型理由没对准成本轴（含评审人自认）**
- 问题：§14 理由列"万级向量 numpy 暴力余弦仍在 50ms 量级"防守的是余弦——那从来不是瓶颈（本轮已核，见第 0 节）。真实成本：~560M 参数模型的常驻内存与冷启动加载，与同一格"明确不选：默认加载大模型（拖慢冷启动）"直接矛盾。ONNX int8 后单条 ~10–30ms 可用，但那是"能用"，不是被论证过的"该默认"。
- 证据/反例：Windows 笔记本冷启动：加载 int8 模型 + onnxruntime 初始化后，首条 recall 延迟从 P0 验收线（<100ms）跳到秒级——验收指标被自己的选型打破。
- 建议改法：§14 该行从"定死"改为"待 P1.5 定"，两个可落点由语料中英混合度数据裁决：(a) bge-m3-onnx-int8（质量优先，接受冷启动成本，明确写进验收影响的豁免）；(b) multilingual-e5-small（117M/384 维/100 语言，注意 query:/passage: 前缀）。两条都不违反零 LLM 硬约束（本地 ONNX，无 API）。

**3. 归档资格的 stale 门槛留下"高置信冷条目"死角，复核队列无界**
- 问题：auto-archive 要求"heat 最低 10% 且 90 天未召回的 **stale** 条目"——stale（低置信）是前置。高置信但冷的事实（历史 decision、一次性约定）永远不会 stale，heat 再低也无出口；复核队列没有溢出策略。
- 证据/反例：一年攒 150 条 decision（全部 1.0 置信、用户确认过、之后从未召回）→ 不 stale 不归档，2000 软上限被"纪念碑条目"吃掉 7.5%，复核队列同源积压——致命 2 的变体以慢速重现。
- 建议改法：归档资格去掉 stale 前置，"heat 最低 10% 且 180 天未召回"即可入选；stale 只是把等待期 180→90 的加速器；pinned 豁免（不可归档）。复核队列 >50 条时最老一批自动转归档候选并告警。

**4. v0.2→v0.3 清扫残留（一致性包，约 30 分钟文案工作量）**
- 问题：(a) §14"并发/版本"行仍写"（可选）git worktree""git 只用于睡眠整合的 diff"，与 9.6"worktree 作废、git 只导出报告与快照"矛盾——实现者照表格做等于死代码复活；(b) INV5"二者必居其一"覆盖不了 Route A 同角色情形（contradicts 边 + 不开仲裁，两头不沾），按不变量断言会永久 fail；(c) INV12"claim 永远不能使他人失效"与 9.3 仲裁终态"claim 胜出 → 输家写 valid_to"冲突，应表述为"**未经裁决**不能使他人失效"；(d) status 枚举里的 `dormant` 全文无任何触发规则（从 human-memory 借来的空状态）；(e) 评审工单"三份关键材料"仍写 INV1–INV10，实际已 12 条。
- 证据/反例：断言 INV5 的测试在"writer 自己的 claim 反对自己旧 observation"场景永远红。
- 建议改法：一轮文案清扫，全部不涉架构。

**5. INV11"本地排队补写"埋了排序坑，已有的 F4 机制是更简单的解**
- 问题：shim 离线排队、daemon 恢复后 flush——这些条目此刻才拿到 seq，与"seq 是唯一合法排序依据"的语义错位（事件顺序 ≠ 写达顺序）；排队文件自身还有崩溃一致性问题要处理。
- 证据/反例：daemon 挂 10 分钟，两个宿主各排队 3 条，恢复后 flush 与在线会话写入交错，events 时序错乱——F4 的 (session_id, path, mtime) 去重能挡重复，挡不住乱序。
- 建议改法：不排队。写入失败即丢弃 + 记 event；靠"宿主 transcript 是事实源"补账——下次睡眠周期重扫 transcript，episode 天然被 F4 幂等去重。fail-open 更彻底，代码更少，INV11 措辞同步简化。

【我不同意你的事实判断】

1. **§14 嵌入行"万级向量 numpy 暴力余弦仍在 50ms 量级"——数字对，守错了门**。本轮核查：bge-m3 为 XLM-R-large 底座 ~560M 参数 / 1024 维 / 8192 ctx（[HF 模型卡](https://huggingface.co/BAAI/bge-m3)）；CPU 生成单条嵌入 PyTorch ~100ms、ONNX ~30ms（[性能对比](https://github.com/yuniko-software/bge-m3-onnx/blob/main/performance_comparison.ipynb)），int8 量化最高再 6×（[Microsoft/ONNX Runtime](https://medium.com/microsoft/faster-and-smaller-quantized-nlp-with-hugging-face-and-onnx-runtime-ec5525473bb7)）。瓶颈在生成与加载，不在余弦；且该默认与同行"不选大模型"自相矛盾（详见重要 2）。
2. **16.2 的"静默跳过率"作为健康指标在方法论上不可测**。沉默无信号：无法区分"用了没说""读了没用""根本没看"。这不是取阈值的问题，是指标不存在。删掉或换可测代理（见重要 1）。

（确认无误项：Claude Code hooks 事件名与 SessionStart stdout 注入语境与[官方 Hooks Reference](https://code.claude.com/docs/en/hooks) 一致，A 档前提成立；v0.3 对首轮四条核查的转述无误。）

【被低估的风险】

**P1.5 校准数据的选择偏差**。B 档靠模型自觉调 recall，漏调率未知且不可观测——你只会拿到"模型想起来调"的那些样本。若真实漏调率高（>50%），攒下的 300 条注入记录是自我选择出来的：越是模型有把握、话题贴近的时刻越容易被记录，0.72 阈值、top-k、12k 预算就校准在有偏分布上，且 tune 脚本的报表会自我感觉良好。对策：P1.5 结束时统计**recall 触发率**（触发 turn 数 ÷ 总 turn 数，分母可从宿主 transcript 数出），作为是否提前 P4a（A 档 hook 自动召回 = 无偏注入）的判据；P0 的 tune 脚本把"触发率"与"命中质量"分开报告，禁止只报后者。
