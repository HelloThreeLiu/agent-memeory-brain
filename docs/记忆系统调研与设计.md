## 1. 结论先行

1. **"四层记忆法"业内没有统一切法。** 现有项目把三条正交轴混着切：认知类型（CoALA）、作用域（会话/项目/全局）、权威与可变性（只读内核/可塑倾向/显式事实）。【C】
2. **但骨架一致**：极小且近乎只读的**内核层** + 会话级**瞬时层** + 原始**事件流水层** + 提炼后的**知识层**。差异只在边界画在哪、晋升阈值怎么定。
3. **最普遍的缺陷不是"记得少"，是"记了不可解释"**：没有一条记忆能回答"我凭什么记着"，也没有恢复通道。可视化项目几乎全是只读快照，和引擎两张皮。
4. **多 Agent 并发里，数据打架已有成熟解，语义污染没有。** 前者用双时间轴 + 边失效（Zep 是事实标准），后者（谁有资格把判断写成事实）我查不到实现，是真空。
5. 设计押三处差异化：**证据链、可回滚、可视化即调试器**。
6. 落地路径：**Python 单进程 + SQLite 单文件 + MCP 接口**。DSH 原生桥接 MCP 且只桥接 Tools【A】，所以不必先写 Cordis 插件；同一套引擎可接 Claude Code / opencode / ZCode / WorkBuddy。

## 2. 术语与分层约定

| 术语 | 含义 | 备注 |
|---|---|---|
| L1 核 / Core | 身份、边界、授权、长期目标 | 只读，提案制，≤800 token |
| L4 星 / Semantic | 事实、偏好、决策、关系、程序 | 长期，只降权不删 |
| L3 尘 / Episodic | 对话链、事件、证据底账 | 天级衰减，有界 |
| L2 场 / Working | 当前会话与召回包 | 会话级，**不落长期库** |
| episode | 一段连续对话 / 一次任务 | 语义记忆的证据单位 |
| factKey | 事实的唯一键（如 `repo.lang`） | 冲突检测的抓手 |
| assertion_type | observation / decision / claim / hypothesis | 决定"能不能当事实注入" |
| invalidation | 事实失效：写 `invalid_at` / `expired_at`，不删除 | 借 Zep 的双时间轴 |
| seq | daemon 分配的单调序号 | **唯一合法的排序依据** |
| scope | global / project / host | 三个正交作用域 |
| lease | 写租约：某 project 同一时刻只一个 writer | 挡并发写的折中方案 |

**分层依据的说明（v0.1 这里自相矛盾过，现修正）**：层的**名字**沿用 CoALA 四类（工作/情节/语义/程序），因为类型决定**算法**（怎么抽、怎么检索）；层的**分界判据**用"权威 × 时间尺度"，因为它决定**写入门与衰减**。两者不冲突：一个管内容形态，一个管权限与生命周期。

## 3. 调研 A：DSH 记忆插件

DSH 插件是 Cordis bundle（`dsh.bundle.patch` → `cordis.patch.yml`）。记忆类插件普遍 v0.1.0、MIT、TypeScript、零外部依赖，兼容 DSH 0.2.x-rc。【B】

### 3.1 dsh-layered-memory（yinling2024）—— 唯一真正以"四层"命名并写清职责的

| 层 | 存什么 | 写入门 | 读出门 |
|---|---|---|---|
| 核心层 | 身份、根本人设、安全边界、授权规则 | 默认只读；仅 `layered_core(propose)` + 用户授权后 `apply`（需 `confirm:"APPLY"`） | 作为系统硬约束注入，不参与普通检索 |
| 内隐层 | 稳定偏好、表达风格、行为策略、技能倾向 | 主模型观察式写入，本地反射累计够证据（`implicit.minEvidence=3`）才晋升 | 作为**风格先验**注入，不陈述为事实 |
| 外显长期 | 重要事件、事实、约定 | 显式工具写入，或短期显著片段晋升；`factKey` 同键只留最新，旧条 `superseded` 但保留 | 每轮按相关度召回摘要；`layered_search` 查细节 |
| 短期 | 最近对话、任务中间状态 | 自动写入，TTL 过期 | 只注入显著片段；过期前可晋升为候选 |

真正值得抄的机制：
- **改内核是协议而非操作**：propose → 展示 diff → 用户授权 → apply → 写前备份 `core/versions/` → 可 rollback；另有 30 秒冷却（`core.applyCooldownSeconds`）。
- **Token 预算显式化**：`recall.topK=5`、`prompt.recallMaxChars=900`、`alwaysFacts=2`。
- **遗忘分阶段**：TTL(30min) → 降权 → 归档 → 回收站(30 天) → 硬删。
- **审计**：`audit.jsonl` 全量留痕。
- **边界**：内隐层不能改核心，冲突写入直接拒绝。

> 评价：样本里**职责划分最干净**的一个——切分依据是"权威 + 可变性"而非"数据类型"。缺点是事件与事实压在"外显长期"一层，靠 `factKey` 打补丁。

### 3.2 dsh-memory-plugin（x-000001）—— 切分依据是"作用域"

四层 `session / project / global / habit`，四个**物理隔离**的存储根，启动时校验不嵌套、不互为别名，否则拒绝启动。【B】

- **渐进披露**：常驻索引硬上限，细节靠 `memory_recall` / `memory_expand` 两级展开；有每会话累计预算与可观测的降级阶梯。
- **缓存友好**：内容签名不变时注入段**字节稳定**，从而复用 prompt cache。
- **习惯学习双门**：observe → threshold → judge(可选，默认关，坏配置 fail-open) → candidate → **人工门 1** → suggested → **人工门 2** → auto；模型无权自晋升，确认只能在宿主 UI。
- **零 LLM 可运行**：无模型路由时写入、召回、注入、遗忘、健康报告照常。

> 值得抄：物理隔离 + 启动校验；"模型无权自我晋升"的双门协议。

### 3.3 dsh-memory-vault（xs1023）—— 切分依据是"压缩层级"

短期（最近 20 条原始消息，每次折叠 10 条）→ 中期（≤4 条摘要，折叠 3 条）→ 长期（≤4 条摘要）→ 永久（当前会话重要内容，不被自动丢弃）。单库 `~/.dsh/memory/memory.db`，按会话工作区归属，检索默认"当前项目 + 全局"。17 个工具。【B】

它自己承认的坑值得记：**层容量参数是耦合的**——一次短期折叠消耗 10 条原始消息才产出 1 条中期消息，中期限额必须远小于短期，否则"中期→长期"永不触发。调参不能只调一个数。

### 3.4 其余样本

| 插件 | 切法 | 特点 | 局限 |
|---|---|---|---|
| dsh-memory-evolve | 短期/长期/核心 + 命名空间 | 权重随使用调整、衰减半衰期、按工作区隔离 | 演化参数多，默认值不一定匹配使用频率 |
| dsh-core-memory | 只做核心层 | "少而稳"，召回更准 | 单独用会显得记得太少 |
| dsh-mnemon | 不分层，代理筛选 | 代理判断什么值得记、检索时挑 | 多一次模型调用，标准不透明时"该记的没记" |
| human-memory | 类型 + 状态机 | 见 3.5 | 规则抽取天花板明显 |

聚合站的一致建议：**不要同时装多个注入式记忆插件**（召回叠加、重复写入、分不清谁干的）。【B】——注意这是**回避**，不是解决。

### 3.5 human-memory（zyj52742-cloud）—— 唯一同时做引擎和星图的项目

不走"四层"叙事，走**类型 + 状态机 + 打分**，机制比多数分层插件细：

- 单表 `memories`：`kind`、`importance`(0~1)、`weight`(动态)、`status`(active/dormant/superseded/deleted)、`pinned`、`trigger_terms`(唤醒线索词)、情绪三维、`decay_class`/`half_life`、`aftermath`(余波期)。
- 重要度七因子：0.25 基础 + 0.28 自我参照 + 0.30 情绪冲击 + 0.12 社会关系 + 0.10 身份目标 + 0.10 状态持续 + 0.08 新奇 + 0.05 细节。
- 召回五因子：`0.45 相关性 + 0.25 重要度 + 0.12 时近性 + 0.10 权重 + 0.08 情绪冲击`；休眠 ×0.35，钉住 +0.25，相关性 <0.10 且未钉住丢弃。
- 半衰期：心结 36500 天 / 身份·边界 3650 / 关系 730 / 偏好 365 / 目标 180 / 习惯 90 / 情绪状态 21 / 事件 10；情绪冲击高则 ×2 或 ×1.5。
- 状态机：`dormant → active` 靠线索相关性 ≥0.25 自动唤醒；`superseded` 用于"同一对象、态度反转"。
- 性能：倒排索引 `memory_terms` 先取候选再算相关性，1 万条 10–45ms。

它的"记忆宇宙"是**导出式只读快照**（`mode=ro` + `query_only=1`）：两张可离线打开的三维视图（关联网络 / 行星星图，八类天体、四旋臂银河、卫星=派生会话）。干净，但**不能反向改记忆**。

## 4. 调研 B：星空 / 神经元风格的可视化项目

| 项目 | 数据源 | 布局范式 | "活"的手段 | 短板 |
|---|---|---|---|---|
| Akasha | Obsidian vault 的 md 链接 | 力导向粒子星系，颜色=知识域，亮线=跨域链接 | 相机飞行、标签随距离淡入 | 只有链接，无语义权重；只读 |
| Knowledge Galaxy | docx/txt/md + LLM 抽实体 | Three.js + react-force-graph 星体 | 节点发光、侧栏 AI 分析 | 一次性生成，无时间维度 |
| BrainClone | 日记/照片 + Gemini 抽取 → Neo4j | react-force-graph-3d + bloom | "Neural Journey" 穿行、悬浮高亮 | 重资产（Neo4j + pgvector + Redis） |
| ai-brain-3d | 手写 NODES 数组 | 脑壳线框 + 解剖分区为锚点 | 突触脉冲、halo 粒子云、空闲 3s 自转 | 单文件 demo，不是记忆系统 |
| mnemoverse memory-viz | 记忆原子 + Hebbian 边 | 力导向 + HDBSCAN 聚簇 | 时间轴快照回放、原型外发光、valence 双色内发光、drift 橙环、单 Points 批渲染 | 面向实验数据，不面向个人 |
| Memory Brain Graph | Obsidian vault + MCP | 太阳系：人物=恒星，其余按连接距离分壳层 | 突触粒子级联点火 | 隐喻与语义不完全对应 |
| quant-memory-palace | 文档 + Qdrant + KMeans | 3D 空间聚类 | 粒子、连线 | 只有聚类，无生命周期 |

可复用的四件事：
- **视觉通道 ↔ 数据字段 1:1 映射**（mnemoverse 最完整）：重要度→大小、类别→颜色、结果→形状、置信/漂移→外环、边权→粗细与透明度。没有这套映射的"星空"就是屏保。
- **三种布局范式**：力导向（关系近则近）、解剖分区（先验语义位置）、轨道（层级/时间）。**轨道半径天然是连续量**，最适合表达层级。
- **三种"活"的手段**：沿边脉冲（召回事件）、节点呼吸（权重）、整体缓旋（空闲态）。低成本高观感。
- **共性短板**：几乎全部只读、无治理入口、无时间回放（只有 mnemoverse 有）、大图撞性能悬崖。

## 5. 横向分析：四层法到底在分什么

### 5.1 三条正交轴被混用

| 轴 | 取值 | 代表 |
|---|---|---|
| A. 认知类型（CoALA） | 工作 / 情节 / 语义 / 程序 | LangGraph、LangMem、Letta、多数论文 |
| B. 作用域 | 会话 / 项目 / 全局 / 习惯 | dsh-memory-plugin |
| C. 权威与可变性 | 只读内核 / 可塑倾向 / 显式事实 / 瞬时 | dsh-layered-memory |

CoALA 的"情节层"与 dsh-memory-plugin 的"会话层"听起来都像"最近发生的事"，但前者是**内容类型**，后者是**隔离边界**。混在一张表里就会出现"这层该不该跨项目共享"这类无解争论。

### 5.2 各层职责的通用范式

| 职责 | 内核层 | 工作层 | 情节层 | 语义层 |
|---|---|---|---|---|
| 回答的问题 | 我是谁、不能做什么 | 现在在干什么 | 发生过什么 | 什么是真的 |
| 容量 | 极小（≤800 token） | 会话级 | 中，有界 | 小-中，精 |
| 写入者 | 人（授权） | 运行时自动 | 运行时自动 | 抽取 + 确认 |
| 频率 | 极低 | 每轮 | 每回合/每话题 | 每次睡眠周期 |
| 衰减 | 不衰减（版本化） | TTL | 快（天级） | 慢（月-年），只降权不删 |
| 读取 | 常驻硬注入 | 拼进上下文 | 按需展开（证据） | 常驻索引 + top-k |
| 失败模式 | 人设漂移 | 上下文膨胀 | 流水账堆积 | 垃圾抽屉、互相矛盾 |

### 5.3 四条数据通路（四层真正的价值）

1. **写入**：会话事件 → 工作层缓冲 → 切段成 episode → 情节层。
2. **晋升**：情节层按热度/重复/明示 → 抽取为语义候选 → 去重与冲突判定 → 语义层；语义层 → 内核层**只能人工提案**。
3. **召回**：内核层常驻（字节稳定）→ 语义层索引 + top-k → 情节层按需展开取证据。
4. **遗忘**：TTL → 衰减降权 → 归档 → 回收站 → 硬删；删除要**传播**。

四层的成本几乎全在**通路的阈值与预算**，不在表结构。

### 5.4 五个共性缺陷（本设计要正面回答的）

1. 语义层与情节层的边界靠抽取质量，抽取差 → 语义层退化成"摘要过的事件表"。
2. 晋升阈值全凭先验，且参数互相耦合（vault 的教训）。
3. 双写 / 多插件叠加导致同一事实被召回多次。
4. 可视化与引擎脱节：导出快照、只读、无法纠错。
5. 无可解释性：没有证据链，用户无法判断"它为什么这么认为"。

## 6. 设计：定位与目标

**一句话**：本地优先、单人使用、可审计的四层记忆引擎，带一个"可视化即调试器"的星图界面。

代号：`nebula-brain`（记忆星野）／`synapse`（突触）／`织微`。下文用 **Nebula** 代称。

**目标（可验收）**

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | 跨会话连续 | 同一事实不重复问第二遍；"上周说的那个"能定位到原始对话 |
| G2 | 有界 | 连续 30 天，每轮注入 token 不随库增长（硬预算 + 降级阶梯） |
| G3 | 可解释 | 任一条 L4 记忆能列出支撑它的原始事件与写入时间 |
| G4 | 可撤销 | 自动写入 30 天内可一键撤销；内核改动永远可回滚 |
| G5 | 离线可用 | 未配置任何模型 API 时，写入/召回/遗忘全链路正常 |
| G6 | **信任可度量** | 注入块有"这条没用 / 错了"的一键反馈；`status` 与睡眠报告输出"注入信任度"（见 16.3） |

**非目标**

- 不做多租户 SaaS、不做云同步、不做团队共享（**支持同一用户的多 Agent 协作，见第 9 节** —— v0.1 这里写得含糊，已修正）。
- 不做通用 RAG 知识库（RAG 检索静态语料，记忆是有状态、会演化的）。
- 不做"每轮调 LLM 抽取"的重方案（成本不可控、结果不可复现）。

---

## 7. 设计：四层划分

按"权威 × 时间尺度"排布，从上到下越来越瞬时：

| 层 | 代号 | 存什么 | 不存什么 | 写入门 | 读出门 | 容量 | 衰减 |
|---|---|---|---|---|---|---|---|
| **L1 核** | Core | 身份、边界、授权、长期目标、硬约束 | 任何具体事实 | 提案 → diff → 人工 apply（+ 快照/回滚） | 字节稳定地硬注入 | ≤800 token | 不衰减，版本化 |
| **L4 星** | Semantic | 事实、偏好、关系、决策、程序 | 原始对话 | 睡眠周期抽取 + 冲突判定；程序需双门 | 常驻索引 ≤300 token + top-k=5 | ≤2000 条（**软上限**，触顶走 auto-archive，见 9.5） | 180–3650 天，只降权；不硬删，可归档 |
| **L3 尘** | Episodic | 对话链、事件、结果、情绪强度、来源 | 提炼后的事实 | 回合结束自动切段 | 不进常驻；按需 expand | 有界（热/温两档） | 天级，热→温→归档→回收站 |
| **L2 场** | Working | 当前会话消息、本轮召回包、任务状态 | 任何要长期留存的东西 | 运行时自动 | 拼进上下文（最近 6 轮） | 会话级 | TTL 30min 空闲 / 会话结束 |

**L4 的三个注入通道**（`channel` 字段，同层不同门）：

| channel | 内容 | 注入方式 | 写入门 |
|---|---|---|---|
| `fact` | 陈述性事实、决策 | 作为事实注入 | 抽取 + 冲突判定 |
| `style` | 偏好、表达风格 | 作为**先验**注入，不陈述为事实 | 观察累积（≥3 条证据） |
| `procedure` | 策略、习惯、工作流 | 默认不注入 | 双门人工确认 |

**与 CoALA 的映射**：L1≈程序性(显式)+身份语义；L2=工作记忆；L3=情节；L4=语义+程序。
**为什么不是五层**：程序记忆与其他长期记忆共享"长期/高权威/低容量"属性，差别只在**写入风险**，用同层不同门表达比多开一层省心。

## 9. 设计：四条通路与阈值

### 9.1 写入

1. 每轮消息进 L2 缓冲（内存 + `session_turns` 临时表，不入 `memories`）。
2. **切段**：话题漂移（与当前 episode 中心相似度低于阈值）或空闲 3 分钟 → 结束 episode 写 L3。
3. L3 只记：原文引用、时间、`heat`、`visibility`、`role`。**这一层不调模型**。
4. 标记候选：`importance` 高 / 用户说"记住" / 同 `fact_key` 反复出现。

**幂等**：写入键 = `fact_key + content_hash`；60 秒窗口内同键同内容 → 合并，`observed_by` 追加，不新建。episode 用 `(session_id, path, mtime)` 去重（F4）。

### 9.2 晋升（L3 → L4）

触发（任一）：`recall_count ≥ 3` / `importance ≥ 0.7` / 用户显式指令 / 同 `factKey` 出现 ≥2 次不同表述。

- 去重：`Jaccard ≥ 0.72` → 强化（`weight +0.08`），不新建。
- 置信：规则抽取 0.6、LLM 抽取 0.75、工具输出 0.85、人工确认 1.0。
- 冲突 → 走 9.3，**不做覆盖**。

### 9.3 冲突与失效（v0.4：三级路由，类型 → 权威档 → 时间）

v0.2 的错误：把"自然更替"和"真分歧"塞进同一条流程——既写 `valid_to` 又"保持 active + 双注入"，自相矛盾（评审致命 1）。现拆成三路，先判类型再执行。

```
路由前置（两条都满足才进入路由）：
  P1 同作用域：新条与旧条必须同 scope + 同 project_id。
     global 键跨项目共享，project 键不跨；跨 scope 的同名键不参与路由 ——
     两个项目各有一条 build.cmd，不该互相"更替"。
  P2 同槽位且真互斥：fact_key 的语义是"唯一真相槽位"，同键即候选冲突，但先判补充还是互斥：
     · 内容包含关系（一方包含另一方）→ 不是冲突，走 merge：evidence 合并、weight 强化，不失效
     · 取值不同 / 否定词互斥 → 进路由
     · 判不出 → 保守走 B（可回滚），两条都记进 audit

同 factKey 且互斥时，按"先看类型，再看权威档，最后看时间"判断。
注意：下面的"档"指 assertion_type 的固定档位（decision 1.0 > observation 0.85 > claim 0.6 > hypothesis 0.4），
不是 memories.confidence 字段的值 —— 混用会造成歧义（v0.3 就混了）。

0) 新条是 hypothesis？
   → 走 A'：只追加，永不仲裁（连跨角色也不）。
   → 理由：默认不注入的推测不该消耗人的注意力；被后续 observation 证实时自然走 B（0.85 ≥ 0.4）。

1) 新条是 claim？
   → 走 A：只追加。写 contradicts 边，旧条一律不动。
   → 跨角色（role 不同）才开 arbitration；同角色只记录，不打扰人。
   → claim 作为写入方永不使他人失效（INV12）。
   → 它能"赢"，但只在用户裁决之后（见下方终态），不是它自己赢的。

2) 新条不是 claim / hypothesis，且 新档 ≥ 旧档？
   → 走 B：按时序静默失效，不开仲裁。
   → 覆盖同类型（obs→obs、dec→dec）与"高覆盖低"（dec→obs、obs→claim、dec→claim）。
   → 旧条 valid_to = 新条 valid_from；expired_at = 当前时刻；superseded_by = 新条 id；
      status 保持 active（有效性看 valid_to，不看 status）。
   → 时间比较按 valid_from 分两种，**不许回退 seq**：
     · 新条更晚（正常更新）→ 旧条 valid_to = 新条.valid_from
     · 新条更早（补录历史）→ 新条 valid_to = 旧条.valid_from，旧条继续是"当前"
   → 只有真不可比（同一时刻 / 无日期 / 解析失败）才回退 seq 定先后。
   → **v0.5 实现期修正**：原文写的是"同日即不可比"，按字面实现会写出倒挂区间——
     旧条 valid_from=18:00、新条 09:00，回退 seq 后旧条 valid_to=09:00，这条历史
     变成"从未成立"，而 `expired_at` 触发器让它再也改不回来。改成按真实时刻比较，
     只有时刻完全相同（或日期级输入）才回退 seq。
   → v0.4 把"顺序颠倒"也算不可比、回退 seq，等于让后写者赢——那是 LWW，正是附录 A.3 废掉 supersede 的理由。

3) 新档 < 旧档？
   → 走 C：开 arbitration(status=open)，两条都不动，召回双注入并标注"见 arb-xxx"。
   → 唯一常见情形：observation 挑战 decision（"我看到的和你定的不一致"）。
```

**为什么不再用"同置信档"做判据**（v0.3 的错）：B 写"≥"、C 写"同档"，obs→obs（0.85=0.85）同时命中两条——按 C 读法日常更新全进仲裁，按 B 读法 C 那条是死文。两种读法必有一坏（二轮评审致命 1）。改成"同类型/高覆盖低一律 B、只有低挑战高才 C"，二义消失。
**组合空间是 4×4=16 格**（不是 5 种）：claim→任何 走 A（4 格）、hyp→任何 走 A'（4 格）、新档 ≥ 旧档 走 B（7 格）、obs→dec 走 C（1 格）。v0.4 的 D.1 只列了 5 种，属于清单不全——这轮自己就没跑全（三轮评审指出）。

**谁被失效**：按 `valid_from` 排序，早的结束——与写入顺序解耦，补历史数据也不会错（借 Zep【A】）。
**裁决优先级**：`用户明确表态 > 可执行验证（测试/构建/运行输出） > 引用具体代码位置 > 主观评价`。前两档可定案；后两档只能保留 claim。
**仲裁终态**（v0.2 未定义，评审重要 4）：
- 输家写 `valid_to`、`expired_at`、`superseded_by`；**行保留、可查历史**，`status` 不变
- 若输家是 claim → `status=archived`、`archived_reason=refuted`
- 若两段时间各自成立 → `resolution=both`，按时间段共存，不判输赢
- 注：终态里"claim 胜出导致对方失效"是**用户裁决的结果**，不是 claim 自身的能力——这正是 INV12 说的"未经裁决不得使他人失效"。

**终态的区间几何**（P1 审查 M-1 补）：`valid_to` 只有一个合法目标——**`>= 输家自己的 valid_from`**。
写成倒挂区间等于宣布这条历史"从未成立"，而 `expired_at` 的不可变触发器让这个错误永远改不回来。
所以边界按赢家的生效位置分三种：

| 几何 | 边界取 | 为什么 |
|---|---|---|
| 赢家更晚生效（9.3-B 的"新压旧"） | 赢家 `valid_from` | 输家在赢家生效那一刻让位 |
| 赢家更早生效（9.3-C 的"旧条胜出"） | **裁决时刻** | 输家从自己生效到被裁决为止**确实被注入过**，这段记录不能抹掉；"它错了"由 `superseded_by` 与 `archived_reason=refuted` 承载，不由负区间承载 |
| 两者时刻相同 / 任一缺失 / 解析失败 | 裁决时刻 | 没有可比的时间，只能以裁决为界 |

P1 的 `_retire_loser` 早先把"赢家 `valid_from`"当成唯一答案，于是 observation 挑战 decision、
用户裁 `left` 时写出的 `valid_to` 早于输家 `valid_from`——正是本节开头反对的病理。

**仲裁队列的作用域**（P0 实现期补，schema v2）：仲裁按**槽位 + 分区**唯一——
`(scope, project_id, fact_key, visibility, session_id)` 上最多一条 `open`。
v1 只按 `fact_key` 建唯一索引，等于让两个项目、两个私有 session 的同名键共用一条
待裁决记录；再加上"A 路只追加、不开新仲裁"的复用逻辑，新挑战者会被挂到别人的
仲裁上，自己既没有记账、召回时又被静默丢掉（P0 二轮审查 M-1）。

**对子失效时的自动终态**（P0 实现期补）：9.3-B 让 open 仲裁的某一侧退出当前区间时
（补录/更替都会），该仲裁按**存续侧**自动终态：`resolution=left|right`、
`resolved_by=system:b-route`、写 `arbitration.auto_resolved` 事件；两侧都不在当前区间
（只能由人工改库造成）记 `both`。不这么做的话，下一个挑战会挂到一条已经没人争的
死对子上——记账还在，但召回的双注入永远触发不了。

### 9.4 召回（每轮按序拼接）

```
[L1 内核块]         ≤800 token，内容 hash 不变则字节不变（吃 prompt cache）
[L4 常驻索引]       ≤300 token：置顶 + 最近变化的 top 8 factKey 一行摘要
[L2 最近 6 轮]      超出压缩进 L3
[L4 召回 top-k=5]   每条 ≤100 字，带署名与 assertion_type
[L3 按需 expand]    工具调用，单次 ≤1500 token
```

注入格式（**防"意见变事实"的最后一道闸**）：

```
[decision|user|3d] 接口统一用 POST（ep-118）
[claim|reviewer|2h|未验证] session.ts:88 并发刷新可能丢更新（ep-241）
[observation|writer|2h] npm test 全绿（ep-243）
```

**候选池谓词**（v0.4 补，二轮评审致命 2：v0.3 只写了"archived 排除"，被取代条照样进 top-k）：

```sql
-- 只取"有效区间覆盖当前时刻"的条目，历史版本不进候选池
WHERE status IN ('active','dormant')
  AND (valid_from IS NULL OR valid_from <= :now)
  AND (valid_to   IS NULL OR valid_to   >  :now)
  AND  /* scope / visibility 过滤 */
```

- 同一 `fact_key` 在 top-k 里**最多占 1 席**。否则换过三次的 `build.cmd` 会占满 5 席里 3 席，还互相打架——G1 当场翻车。
- **席位归谁：按档位固定优先 `decision > observation > claim > hypothesis`，同档才比综合分**（v0.5 补）。v0.4 只说"1 席"没说归谁，存在一条真实的翻车路径：用户已定"接口用 POST"（decision），同角色 agent 追加反对的 claim（9.3-A 不开仲裁），两条同时有效且不属双注入例外；等 P1 开了时近性因子，新写的 claim 天然占优 → 注入只剩"[claim|未验证] 接口方法存疑" → agent 回头再问用户一遍，G1 当场破（三轮评审）。
- **落选方不许静默吞掉**：若落选的是与占席条 `contradicts` 的条目，注入时附一行指针——"另有 1 条未验证异议（expand 查看）"，不展开内容、只给 15 个 token。这是对 F2 的最低保证：档位不高的反对意见可以不进正文，但不能消失。
- 唯一双注入例外：open arbitration 的对子（与 9.3-C 一致）。
- 已失效条与更早版本只经 `expand` 工具与时间视图访问。这正是双时间轴的卖点，v0.3 只是忘了把它写成查询规则。
- `pending` 已从 `status` 枚举删除：待裁决由 `arbitration.status=open` 表达，memory 自身保持 `active`。v0.4 留了个没有进入/退出条件的 `pending`，"已记住但检索不到"的窗口期对 G1 是净损失（三轮评审）。

打分（P0 只用前两项，其余按数据逐步开）：

| 因子 | 权重 | 何时启用 |
|---|---|---|
| 相关性 | 0.40 | P0 |
| 重要度 | 0.22 | P0 |
| 时近性 | 0.14 | P1 |
| 权重 | 0.10 | P1 |
| 置信（含 assertion_type） | 0.08 | P1 |
| ~~突触扩散~~ | 0 | **已删除**（评审重要 5）：0.06 权重是噪音，且是为可视化好看反向侵蚀检索。共激活只留在 `memory_links.co_activation` 供画画用 |

层系数 L4×1.0、L3×0.7；`pinned +0.25`；`archived` 排除；`相关性 <0.10` 且未钉住丢弃。

**降级阶梯**（单会话累计 ≤12k token）：L0 全量 → L1 只索引+top3 → L2 只内核+最近 2 条 → L3 只内核，并在界面明示"本轮记忆已降级"。降级必须可见。
**前缀约束**（评审核查【A】）：`字节稳定` 只是必要条件——cache 命中还要求注入块位于 prompt 最前面、且它之前的内容逐字节不变。所以 L1 必须排在最前，动态内容不许插到它前面；这条要写进 adapter 的注入契约。

### 9.5 遗忘（四段阶梯，可回滚）

| 层 | 规则 |
|---|---|
| L2 | TTL 30min |
| L3 | `heat` 半衰期衰减；`heat<0.15` 且 30 天未触达 → archived；再 90 天 → 回收站；再 30 天 → 硬删 |

| 用户指令 | `forget` → 回收站 30 天，可视化显示"已熄灭但可复原" |

### 9.6 睡眠周期（v0.3 改回事务，v0.2 的 worktree 方案作废）

① 处理未消费 episode → 候选 ② 去重合并 ③ 冲突检测 ④ 重算 heat/weight ⑤ 孤立节点降权 ⑥ 写 snapshot。

**执行方式**：daemon 内**一个事务**跑完 ①–⑥，产出可读报告。v0.2 说"直接写库会读到半成品"是**错的**——INV1 已保证 daemon 唯一写者，WAL 下读者拿的是一致性快照，未提交的整合对读者不可见（评审已核实【A】）。worktree+diff 那套是 Letta 的做法，前提是"记忆=git 里的文本文件"，而我这里是 SQLite 二进制单文件，`git diff` 根本不可读，条件不成立。
**git 的定位**：只用于**导出**——diff 的对象是报告与 `snapshot` JSON，不是库文件。
**约束**：幂等 + 可 dry-run + 报告（写了什么、合并了什么、降权了什么、为什么）+ 失败整体回滚。
**附带收益**：顺手消掉 Windows 长路径与多进程 spawn worktree 的坑。

## 10. 设计：跨宿主

### 10.1 结论：不是只能长在 DSH 上

决定"能不能移植"的不是宿主是谁，而是宿主给不给两样东西：**工具暴露**（MCP 是事实标准）与**上下文注入**（hooks 或指令文件）。据此三档：

| 档 | 宿主具备 | 召回怎么发生 | 体验 |
|---|---|---|---|
| A | MCP + 生命周期 hooks | hook 自动注入，模型无感 | 接近原生 |
| B | 只有 MCP | 靠指令块驱动模型主动调工具 | 能用，但会漏 |
| C | 只有指令文件 | 定期导出静态 markdown | 有损兜底 |

引擎只写一次，接入靠适配器。

### 10.2 各宿主能力矩阵（版本相关，别照抄）

| 宿主 | 工具层 | 每轮注入 | 项目级配置 | 指令文件 |
|---|---|---|---|---|
| DSH | MCP（`dsh-mcp-client`，**只桥接 Tools**）或 Cordis 插件 | 插件可注入系统提示 | `cordis.patch.yml` | 插件自管 |
| Claude Code | `~/.claude.json` 全局 / `.mcp.json` 项目 | hooks：SessionStart、UserPromptSubmit、Stop 等 | `.mcp.json` + `.claude/` | `CLAUDE.md`（用户级 + 项目级） |
| opencode | `opencode.json` 顶层 `mcp`，`type:"local"`，command 是数组 | 插件目录自动加载，`session.created` 等 hook | `opencode.json` | `AGENTS.md` |
| ZCode | `~/.zcode/cli/config.json`，**支持从 Claude Code / Codex / opencode 导入 MCP** | 同文件 hooks；subagent 可注入 AGENTS.md | `./.zcode/config.json` | `~/.zcode/AGENTS.md` + 项目 `AGENTS.md` |
| WorkBuddy | `~/.workbuddy/mcp.json` | hooks + 技能 | `.workbuddy/` | 项目规则文件 |
| Codex | MCP + 插件 | 插件 hook（需 `/hooks` 授权） | 项目配置 | `AGENTS.md` |
| Cursor | MCP（`servers` 键） | 无通用 hook | `.vscode/mcp.json` | `.cursor/rules` |

工程实证：`agent-memory` 的 opencode 适配器注册了 22 个 hook，并按**每个 session 的目录**解析项目（git toplevel 名）【B】——说明"抓全量事件 + 按 git 根归项目"可行。

### 10.3 三个必须先定的架构决定

**决定一：单 daemon + N 个 stdio shim。**
每个宿主会 spawn 一个 MCP 子进程；若都直连 SQLite 就是多写者，WAL 能扛但会丢事件顺序，且"会话预算"这类跨进程状态失效。正解：一个常驻 daemon 持唯一写者，各宿主指向一个几十行的 stdio shim。代价是多一个常驻进程。

**决定二：记忆不写进 `CLAUDE.md` / `AGENTS.md`，只放"指针块"。**
有相反路线（`agentsmd-memory`）把记忆直接写进 AGENTS.md，优点是能进 git diff；缺点是膨胀、污染仓库、多人必冲突、无衰减——一个文件装不下四层。我的选择：指令文件只放 5 行固定内容（"你有记忆库，会话开始 recall，学到结论 remember"）。**文件是说明书，不是存储。**

**决定三：作用域是三元组，不是一层。**
`global`（跨宿主跨项目）/ `project`（同 repo 跨宿主共享）/ `host`（某宿主专属）。混成一个 `profile` 字段，会导致"换工具就失忆"和"换项目还记得别的项目"同时发生。

### 10.4 分项目算法

```
project_id = sha1(git_remote_url or realpath(git_toplevel))[:12]

解析优先级：
  显式参数 project=<id|name>
  > MCP roots（宿主声明的 workspace）
  > 会话 cwd
  > 从 cwd 向上找最近 .git → 用 toplevel
  > 都没有 → cwd 的 realpath（标记 loose project）
```

- **monorepo**：默认最近 git root；拆分时在子包放 `.nebula/project.json` 覆盖。
- **非 git 目录**：用路径 hash，换盘符就丢——文档里要明说。
- **检索默认**：`global + current project`；跨项目必须显式传参，**默认关闭**。
- **泄漏防护**：跨项目召回默认关、条目可标 `sensitive`、导出按 scope 过滤、可视化按 scope 分色。

### 10.5 每档的注入落法

| 档 | 落法 | 注意 |
|---|---|---|
| A | SessionStart 注入核心块（字节稳定）+ 项目索引；UserPromptSubmit 注入 top-k 摘要；Stop 触发写入/睡眠 | hook 里**不能**调模型，只做确定性组装；**L1 必须排在最前缀**，否则 cache 不命中（见 9.4） |
| B | 指令块写"何时必须 recall"；工具描述写清触发条件 | 命令式措辞比"你可以…"有效；接受漏调 |
| C | 生成 `MEMORY.md`（top 20 + 指针） | 标注"这是快照，可能过期" |

每宿主一套 `adapter.config`：`topK`、`maxChars`、`injectOn`（session/prompt/both）、`scopeDefault`。小窗口本地模型与 200k 上下文的宿主，预算差一个数量级。

### 10.6 读路径的可见性口径（P1.5 落地，R-8 收口）

P0/P1 的 `expand` / `explain` 是**本地 CLI 工具**，调用方就是库的主人，所以没有做分区过滤。
P1.5 把它们变成 agent 工具之后，这个前提消失了：任何宿主会话都能凭一个 id 读到别的
session 的私有片段、以及跟当前项目无关的条目。这不是"以后再说"的口子，是接宿主前必须
定死的东西。

**口径：一句话——读路径与召回同一条谓词。**

| 维度 | 规则 |
|---|---|
| `visibility` | `shared` 对所有调用方可见；`private` 仅当 `session_id == viewer_session` 可见。调用方没有 session 身份时，private **一律不可见** |
| `scope` | `global` 恒可见；`project` 仅当 `project_id == 当前 project`（调用方没给 project → 只看得到 global）；`host` 仅当 `host == 当前 host` |
| 连带数据 | 历代版本（同 `fact_key`）、`memory_links` 两侧、`events` 行全部按同一规则过滤。`events.scope/visibility` 为 NULL 的历史行视为"归属未知"，**不返回**给工具调用方 |

**"不可见"必须显式说出来，不能静默返回空。** 静默返回空与"这条不存在"无法区分，
调用方会以为记忆丢了。所以 `expand` 命中一条不可见的条目时返回一句
"该条目对当前调用方不可见（scope/visibility 不匹配）"，**但不含 content、不含历代版本**。

**逃生口只留给本地 CLI。** `nebula expand --show-all` 可以在本机看全部；MCP 工具
不暴露这个开关——agent 不该有"看全部"的能力，那是把分区做成摆设。这条与 §10.4
"跨项目召回默认关"是同一个取舍：默认关闭，显式打开，打开的动作留痕。

## 11. 设计：多 Agent 协作

> 场景：ZCode 写代码 / WorkBuddy 审查；Claude Code 写文档 / opencode 审查。同一项目、多个宿主、交叉验证。

### 11.1 三种"并发"，只有一种真危险

| 类型 | 场景 | 后果 | 是否要防 |
|---|---|---|---|
| 读并发 | 两个宿主同时召回 | 无害，各拿快照 | 不用锁 |
| 写并发 | 两个会话同时写 | 静默出错：重复条目、互斥双活 | 必须防 |
| **语义并发** | 两个 Agent 对同一事给出不同判断 | 认知污染 | 最难，最该防 |

### 11.2 四个故障模式

- **F1 互斥双活**：两条同 `factKey` 互相 supersede → 都死，或都活但答案矛盾。
- **F2 意见变事实（最危险）**：审查者说"这里并发会丢更新"，被抽成 `fact`；下次写作者当真去改本来没问题的实现，或把真 bug 当"有人提过"跳过。
- **F3 回声室**：A 的猜测 → B 引用 → A 再引用，三轮后置信度 0.9，实际零验证。
- **F4 流水账爆炸**：同一段对话被三个宿主各记一遍，`heat` 被重复计数推高，晋升阈值失真。

### 11.3 四条机制

**署名与断言类型**（`assertion_type` 决定能否当事实注入）：

| 类型 | 来源 | 可作事实注入 | 置信上限 |
|---|---|---|---|
| `observation` | 文件内容、命令输出、测试结果 | 是 | 0.85 |
| `decision` | 用户明确表态 | 是 | 1.0 |
| `claim` | Agent 的判断/建议 | **否**，必须标"未验证" | 0.6 |
| `hypothesis` | 推测 | 否，默认不注入 | 0.4 |

**幂等写入**：`fact_key + content_hash`，60 秒窗口合并。**单写者 + 会话租约**：daemon 发租约，写入带单调 `seq`。**冲突不覆盖**：建 `contradicts` 边 + 裁决队列（见 9.3）。

### 11.4 角色权限矩阵

| 角色 | 典型宿主 | 可写 | 不可写 | 召回偏向 |
|---|---|---|---|---|
| writer | ZCode / Claude Code | observation、handoff、claim | decision | 项目决策、已知坑、接口约定 |
| reviewer | WorkBuddy / opencode | claim（stance=objection/support） | decision、覆盖他人 observation | 最近变更、历史同类问题、上次审查结论 |
| observer | 任意只读客户端 | 无 | 全部 | 只读 |

这条解决 F2：**审查者写不出 fact，只能写 claim；claim 变 decision 只能经用户（role=user）。** v0.2 写的"或被审方接受"是后门——writer 也是 LLM，它接受 reviewer 的错误 claim 就合法造出一条 1.0 的 decision，回声室由此转正（评审重要 2）。若 writer 认为该 claim 成立，正确路径是它自己跑一次验证、以 `observation` 记录（≤0.85）。

### 11.5 交接协议（handoff）

交叉验证的成败几乎全在交接单。不要让审查者靠猜：

```yaml
kind: handoff
changed: [src/auth/session.ts]
why: 修 #412 的 token 过期竞态
watch: 并发刷新路径（refresh 与 logout 同时触发）
known_risk: 没加锁，靠单线程假设
verify_with: npm test -- session
```

状态机（单向）：

```
claim ──user accepted──> decision ──> fact（被工具输出验证后）
  │                          └─ agent 自己认可？→ 只能升为 observation（≤0.85）
  └──rejected──> archived（保留，可查"当时为什么否掉"）
```

### 11.6 分级落地：别一上来做分布式系统

关键判断：**"ZCode 写、WorkBuddy 审"绝大多数时候是人在串行切换，不是真并发。** 真并发只发生在"后台任务还在跑，我已经切走"。

| 级别 | 形态 | 需要什么 | 成本 |
|---|---|---|---|
| L1 顺序多 Agent | 人切换窗口，同时只有一个在写 | 会话归属、角色权限、handoff、注入署名 | 近零，随 P4 做 |
| 折中：写租约 | 同一 project 同时只一个 writer（30min 可续），其余只读或追加 claim | lease 表 + 拒绝写入的提示 | 几十行 |
| L2 真并发 | 两进程同时写 | 租约 + seq + 幂等 + 裁决 + 冲突可视化 | 高，放 P5 |

### 11.7 收益判断

**共享结论，不共享过程。** L4 共享；L3 按会话隔离（同项目可查但不自动注入）；L2 完全不共享。值得共享的：项目决策、踩过的坑、接口约定、上次审查结论。不值得：工作流水、中间推理、逐文件修改细节。

## 12. 设计：可视化

**核心主张：可视化不是装饰，是调试器。** 人眼对"哪颗星变暗了"极敏感，对一行日志不敏感。所以星图必须能回答问题和被操作。

### 12.1 三个视图 + 一条时间轴

| 视图 | 回答什么 | 关键元素 |
|---|---|---|
| 宇宙视图（全局） | 我的记忆长什么样、哪些在变暗 | L1 在中心（引力核）；L4 恒星（位置=语义相似，颜色=Louvain 簇，大小=log(importance)，发光=weight，外环=confidence，形状=kind）；L3 星尘带（轨道=episode 时间）；待晋升候选=带尾迹彗星 |
| 神经视图（局部） | 这条记忆怎么被想起来的 | 选中 → 激活扩散动画；突触=共激活边，粗细=co_activation，脉冲=召回回放；证据链高亮连回 L3 |
| 时间视图（回放） | 它是不是忘了我上周说的 | 拖 `snapshots` 时间轴；看单颗星的"亮度曲线"：何时被召回、何时失效、何时降权 |
| 治理（横切） | 我要纠正它 | 点击 → 看原文证据 → 钉住/合并/改 kind/遗忘/设为 procedure（走双门） |

### 12.2 视觉语法（1:1，必须带图例）

| 数据字段 | 视觉通道 |
|---|---|
| importance | 半径 = log(1+imp) |
| weight（衰减后） | 发光强度 |
| 最近召回 | 色温（冷=久未触达） |
| confidence | 外环宽度 |
| kind | 形状（球=事实，环=偏好，棱=决策，彗星=待验证） |
| assertion_type=claim | 虚线外框（未验证） |
| 主题簇 | 色相 |
| co_activation | 边粗 + 脉冲频率 |
| 已失效（`valid_to` 非空） | 虚线外框 + 降饱和，**留在原位**（"过期"≠"记不清"，与 archived 区分） |
| status=archived | 暗红、脱离主轨道、可一键复原 |
| 层级 | 到中心的引力距离 |

### 12.3 性能与实现

- 目标 1 万节点 60fps；>3000 节点切单 `Points` 批渲染，仅 hover 补 label。
- **布局离线预计算**（服务端算力导向 + 分簇），前端只做增量与相机。
- LOD：远景只要点云与簇外壳，近景才加载文本与边。
- 数据契约：`GET /graph?snapshot=ts` → `{nodes:[{id,layer,kind,x,y,z,imp,weight,conf,status,label,atype}], links:[...], meta:{ts,counts}}`

**反模式**：粒子越多越好；无图例；每帧重排导致"星在漂"；把 L2 画进星图；只有渲染没有交互。

## 14. 技术选型

| 层 | 选择 | 理由 | 明确不选 |
|---|---|---|---|
| 引擎语言 | Python 3.11+，标准库为主 + 可选 numpy | 文本/抽取/调参迭代最快；human-memory 证明零依赖可跑 | 一上来写 TS/Rust |
| 存储 | SQLite（WAL）+ FTS5 | 单文件、可拷贝、可 SQL 审计、备份=复制 | PostgreSQL（单机无收益） |
| 向量 | 先 numpy 暴力余弦；>5 万条再上 `sqlite-vec` | 1 万条暴力 <50ms | Milvus/Qdrant（运维 ≫ 收益） |
| 图 | `memory_links` + 递归 CTE | 万级节点，图库是过度设计 | Neo4j（BrainClone 需要是因为它做多用户 web 服务） |
| 嵌入 | **P0–P1.5 不用向量**：FTS5 BM25 + 中文 2-gram。P2 之后再按数据决定要不要上，候选 `multilingual-e5-small`（117M / 384 维 / 100 语言，需 `query:`/`passage:` 前缀）或 `bge-m3-onnx-int8`（质量更好，代价是数百 MB 常驻 + 秒级冷启动） | v0.3 把 `bge-m3` 定成默认是错的：我用"万级向量余弦 50ms"辩护，但余弦从来不是瓶颈，真实成本是生成与加载，且与右边"不选默认加载大模型"自相矛盾（二轮评审事实判断 1）。万级数据下词法召回大概率够用，先用数据说话 | 把向量当必需品提前引入 |
| 抽取 | 规则优先；LLM 显式开关、默认关、失败回退 | 成本可控、可复现、断网可用 | 每轮调 LLM |
| 并发/版本 | daemon + SQLite 事务（单写者） | 睡眠整合在一个事务里跑完（9.6）；**worktree 方案已作废** | 自研 CRDT（收益低）/ git worktree（二进制库没有可读的 diff） |
| 接口 | MCP stdio + CLI + 本地 HTTP | DSH 原生桥接 MCP【A】 | 一上来写 Cordis 插件（接口在 rc） |
| 前端 | Vite + React + TS + three.js + 3d-force-graph + postprocessing | 生态最省事，内置 bloom/粒子/相机飞行 | 自研 WebGL 引擎 |
| 布局 | d3-force-3d + 分层向心力；Louvain 离线分簇 | 层级需要自定义力；分簇不能在前端算 | 每帧重算 |
| 打包 | Windows 优先：uv + `python -m nebula`；可选 PyInstaller | 单人维护，先保证能跑 | Electron（先用浏览器 + 本地端口） |

**DSH 接入注意**【A】：`dsh-mcp-client` **只桥接 Tools**——Resources 与 Prompts 没有消费者。记忆注入不能设计成 MCP resource，要么走工具返回值，要么写一个小 TS 插件做系统提示注入。

## 15. 路线图

| 阶段 | 目标 | 产出 | 验收指标 | 主要风险 |
|---|---|---|---|---|
| **P0 骨架**（~1 周） | 能存、能召回 | schema + M1/M2(规则)/M3/M4(两因子) + CLI | 200 条种子；20 个查询命中 ≥70%；召回 <100ms；断网可用 | 权重拍脑袋 → 先跑起来再调 |
| **P1 生命周期**（1–2 周） | 会晋升、会忘、能追责 | M5/M6：晋升、失效、合并、遗忘阶梯、睡眠周期、`explain` | 连跑 500 轮库不膨胀；每条 L4 ≥1 条 evidence；`forget` 30 天内可恢复 | 阈值耦合 → 一次只调一个参数 |
| **P1.5a 接入面**（3 天） | 把引擎变成"宿主能调的东西" | schema v4（`injection_log` / `feedback`）+ MCP stdio 四工具 + 读路径可见性口径（§10.6）+ `project_id` 解析 + 指针块生成器 | `initialize → tools/list → tools/call` 全流程可跑；每次 `recall` 落注入日志；private 条目对无 session 调用方不泄漏原文；指针块重复安装幂等 | 自研 MCP 层与宿主实现的协议差异 → 只做最小必需方法 |

| **P2 可视化 v1**（1 周，原 1–2 周压缩） | 看见 | 快照导出 + 宇宙视图最小版 + 时间轴回放 | 1 万节点 ≥50fps；冷启动 <2s；点任意节点见证据链 | 性能悬崖 → 预计算 + 批渲染 |
| **P3 可视化 v2**（~2 周） | 能治理 | 神经视图、钉住/合并/遗忘/内核提案审批 | 所有治理动作走 WriteService；每次操作有事件 | 旁路写入 |

**顺序不能换**：P0/P1 是"能用"，P2/P3 才是"好看"。先做星图会得到一个漂亮空壳——这是这类项目最常见的死法。

**P5 之前不要接第二个宿主**：P1.5 只接一个，用来攒日志；正式多宿主仍从 P4 开始。

## 16. 风险与未决问题

### 16.1 已知风险

1. **抽取质量是天花板**。规则版抓不到"说不上来哪里不对"。对策不是换大模型，而是**让人一键纠正**，把人的纠正当最高置信信号。
2. **阈值全是先验**。必须配召回日志 + `tune` 脚本用真实数据调，否则永远在猜。
3. **层数越多边界争议越多**。砍到四层、程序记忆共用 L4，就是为少一处边界。
4. **一个人做"四层 + 星图"容易两头空**。只能保一头时保 P0/P1。
5. **生态在 rc 阶段**。引擎不绑 DSH，只通过 MCP 这种稳定边界接触。
6. **"类人脑"是隐喻不是科学**。别在文档里暗示它模拟人脑；它模拟的是"分级存储 + 衰减 + 线索唤醒"这套工程策略。
7. **多 Agent 的语义模型是自创**（见 11.3 / Q5），没有同行实现可对照，最可能白做。
8. **P1.5 的校准数据有选择偏差**（二轮评审）。B 档靠模型自觉调 recall，漏调率不可观测——你只会拿到"模型想得起来"的样本。若真实漏调率 >50%，调出来的 0.72 / top-k / 12k 全是在有偏分布上拟合的，而 tune 报表会一片祥和。对策：统计**recall 触发率**（触发 turn ÷ 总 turn，分母从 transcript 数），触发率过低就别急着调参，先把 P4a 的 A 档自动召回提前。

### 16.2 信任静默衰减（评审新增，我认可是本版最被低估的风险）

**现象**：注入一两次坏记忆（stale 事实与当下现实冲突），用户就开始跳过记忆块、把它当噪音——但每轮约 2k token 照付，G2 有界、G3 可解释、G4 可撤销全部绿灯，**没有任何指标度量"用户已经不信了"**。系统在所有验收指标通过的同时归零。

**为什么比"记错"更危险**：记错可发现、可纠正；不信任不可见、不可逆——用户不会来报告，他只会不再看。

**对策**（已进 G6 与 M12）：
1. 反馈入口放在**注入点本身**，不放在星图里——星图是周更，注入是每轮。GUI 宿主可以是每条后面的"没用 / 错了"；**B 档没有按钮可放**（注入是工具返回的文本），所以做成第 4 个 MCP 工具 `feedback(id, kind)` + 一条 CLI 斜杠命令，用户在对话里说"这条记错了"由模型代调。代价：P1.5 多半天。
2. `injection_log` 记录每轮注入的 id 与字数。健康指标只用**可测代理**：**负反馈率**、**recall 后续 turn 的 expand 调用率**、**注入条被引用数 ÷ 注入条数**。删除"静默跳过率"——沉默没有信号，无法区分"用了没说""读了没用""根本没看"，那不是阈值问题，是指标不存在（二轮评审）。
3. 负反馈率连续超阈值 → 自动收缩注入（降 top-k、砍 `alwaysFacts`），并提示"记忆质量下降，是否进入复核"。
4. 每周一份五行摘要："这周我记住了什么、忘了什么、哪条被纠正"——给人继续信任的理由。

这条也说明"可视化即调试器"不够：调试器要人主动打开，信任靠每轮被动接触维持。

### F.3 与设计文档字面不一致的三处（有意为之）

1. **L4 半衰期按 `kind` 分档**（decision 3650、relation/procedure 730、preference/fact 365、handoff 90、event 30）。§9.5 只给了 180–3650 的区间，没有分档表；这是先验值，P1.5 拿到真实召回日志后应整表复核。
2. **时近性因子不启用**。§9.4 的因子表把时近性（0.14）标为 P1。实现里只开了 weight 与 confidence：时近性会惩罚长期有效的 decision，与 G1（同一事实不问第二遍）正面冲突；而且 `last_recalled` 到这一轮才开始有数据，此时调参等于用空样本拟合。
3. **`resolution=merged` 不开放**。§8.1 的枚举里有它，§9.3 没有定义"合并后正文归谁"。P1 的 `resolve_arbitration` 显式拒绝，而不是猜一个合并结果。

### F.4 落地时被用例与审查抓出的错

- 容量归档的排序写成按元组首元素（`id`）排，实际会归档"最早写入的"而不是"最冷的"。改为显式 `key=heat`。
- `pinned` 一度被当成"连 heat 都不结算"。正确语义是：置顶只豁免"因冷被埋"，heat 仍要记录真实冷度，否则取消置顶的瞬间它会带着过期热度直接掉进归档。
- 裁决终态把"赢家 `valid_from`"当成唯一边界，在"旧条胜出"时写出倒挂区间（P1 审查 M-1）。规格已补 §9.3「终态的区间几何」，实现改为按几何取边界。
- 容量归档的候选池混入 dormant，与"水位只数 active"不同口径，导致触顶跨轮不收敛（P1 审查 m-5）。候选池收敛为 active。
