## 0. 评审方法与事实核查披露

评审中的判断分三类，可信度来源不同：

1. **内部一致性判断**（只需读文档本身即可证伪，不依赖外部事实）：
   致命 1（9.3 步骤 2 与步骤 4/5 自相矛盾）、致命 2（INV3 × 2000 上限 × 复核队列无触顶行为）、
   致命 3（路线图中真实使用排在第 7 周后，与 U1–U3/Q7 的"等真实数据"矛盾）、
   重要 2（11.4"被审方接受"与 INV6 的口径）、重要 3（daemon 不可用行为未定义）、
   重要 4（status=active 但 valid_to 已写的逻辑有效性语义）、重要 5（召回日志缺位于 P0 验收）。
2. **外部事实判断**（首轮凭训练知识做出，**已联网补验，全部成立**）：

   | 声明 | 核查结果 | 出处 |
   |---|---|---|
   | Letta Context Repositories 的 worktree 做法绑定"记忆 = git 中的文本文件"，不能平移到 SQLite 单文件 | ✅ 成立。官方描述：memory（core blocks / skills / notes）以文件形式存于 git 仓库，branch/worktree 为每个 agent 提供隔离副本做并行，合并回主库 | [Letta changelog](https://docs.letta.com/reference/changelog)、[letta-code-sarah 仓库](https://github.com/letta-ai/letta-code-sarah) |
   | SQLite WAL 下读者获得一致性快照，未提交的整合对读者不可见，"读到半成品"不成立 | ✅ 成立。官方 isolation 文档：WAL 模式为快照隔离，读事务开始后看到不变的快照 | [Isolation In SQLite](https://www.sqlite.org/isolation.html)、[Write-Ahead Logging](https://www.sqlite.org/wal.html) |
   | "字节稳定 → 复用 prompt cache"并非自动成立，还需注入块位于各轮 prompt 的相同前缀位置 | ✅ 成立。官方：cache 命中要求 cache_control 块之前（含）的全部文本与图像逐字节一致；稳定内容放前缀、动态内容放后 | [Prompt caching – Claude Platform Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) |
   | bge-small-zh-v1.5 对中英混合 dev 语句是真实瓶颈 | ✅ 成立。512 维 / 最长 512 token / zh 专用；BGE 系混合语料方案是 bge-m3（101 语言、1024 维） | [Xinference 模型页](https://inference.readthedocs.io/en/v1.16.0/models/builtin/embedding/bge-small-zh-v1.5.html)、[BAAI 模型页](https://model.baai.ac.cn/model-detail/100112) |

3. **低风险工程判断**（未联网核查，出错代价小）：
   three.js 单 Points 批渲染 1 万节点 60fps（业界常识量级）；低端核显 + bloom 后处理是真实预算风险。

核查副产物（两条实现备注，非评审意见）：
- WAL 偶发锁短命读者，实现时设非零 busy_timeout 即可（[Hynek TIL](https://hynek.me/til/sqlite-read-only-wal-locked)）。
- 若中英混合确为主流语料，bge-m3 是对 bge-small-zh 的同级替换项（同为 ONNX/CPU 可跑，1024 维，万级数据 numpy 暴力余弦仍在 50ms 量级内）。

**未核查的部分**：原文档标【B】的 DSH 插件调研（附录 B 待核实清单）。工单明示"不必逐字核对调研事实"，且这些不影响本评审任何一条结论——致命问题全部来自文档内部矛盾与工程判断，不依赖 DSH 事实的真伪。

## 1. 九问逐条

| # | 判断 | 一句话依据 |

| Q1 | 名义四层、存储三层，无伤 | L2 不落库，本来就是上下文组装器；L1/L4 的分离（提案制 vs 自动写）无论如何值得保留。"程序层是个字段"恰是优点——差异只在写入门，单开一层要复制衰减、晋升、检索三套逻辑 |

---

【结论】**改后做**——核心押注（bitemporal SQLite + MCP 单边界 + 跨宿主单库）成立且是真空白，但三处规格窟窿必须在 schema 冻结前补上，否则 P1 返工。

【致命问题】

**1. 9.3 一条流程里混了"失效"和"裁决"，没有分流规则**
- 问题：步骤 2 给旧条写 `valid_to`（已失效），步骤 4/5 却"两条都保持 active、都注入"。自然更替（无需人）与真分歧（需要人）共用一条流，什么时候走哪半没定义；INV5 又把 arbitration 定成断言级不变量。
- 证据/反例：单用户单宿主，两周内包管理器 npm→pnpm→bun，三次同 `fact_key` 写入。按现文开三条仲裁、召回时双注入标"存在分歧"——其中两条早已无异议。第三周用户开始无脑点 resolved，Q5 担心的事以这种方式发生。反过来若全走静默失效，reviewer 对 writer 的质疑（F2）会被静默吞掉。
- 建议改法：默认走时间失效（新条 `valid_from` 更晚且置信档 ≥ 旧条 → 写 `valid_to/expired_at/superseded_by`，不开仲裁）；仅两类进仲裁——跨角色 `contradicts`、同置信档且 `valid_from` 不可比。INV5 相应收窄到这两类。

**2. "只降权不删" × ≤2000 上限 × 复核队列，三者组合没有触顶行为**
- 问题：INV3 禁删、容量 2000、队列靠人清——到上限时写入被拒还是挤占？队列无人看时 stale 条目永远 `active`。U1 承认增速未知，但这不是可以留到实测的问题，schema 冻结前必须定。
- 证据/反例：日均 5–10 条候选，半年逼近上限；复核队列积压 200 条；stale 事实只要相关性不恰好低就照样进 top-k=5，"两年僵尸库"以半年计提前到来。
- 建议改法：L4 引入**可逆 auto-archive**（heat 最低 + 90 天未召回的 stale 条目转 archived），行保留、可视化"已熄暗可复原"——不违反 INV3 的精神，把 INV3 措辞从"不删"改成"不硬删，可归档"；定义触顶时的批量归档策略与告警。这是给 9.5 的 L4 行补一条规则，不新增模块。

**3. 路线图让真实使用来得太晚，校准数据滞后于需要它的阶段**
- 问题：U1/U2/U3、Q7 全说"等真实数据"，但按 P0→P5，第一个宿主（P4）在第 7 周后；P2/P3 三四周可视化是在 200 条种子数据的库上调的。
- 证据/反例：P2 验收"1 万节点 ≥50fps"，真实库只有几百条；P3 治理视图针对的队列在实际使用前是空的；到 P4 才发现 0.72 阈值 / 30min 租约全不对，回头返工 P1 的生命周期参数。
- 建议改法：P1 后插入 **P1.5 单宿主 B 档接入**（指令块 + `remember/recall/expand` 三个工具，3–5 天），挤掉 P2 的第一周（P2 压缩为"快照导出 + 宇宙视图最小版"）；从第 3 周起积累召回日志与队列数据，P2/P3 用真实数据调试。

【重要但非致命】

**1. worktree 睡眠整合改事务**：见事实判断 1（已核查）。落法：daemon 内一个事务跑完 ①–⑥，产出既有的可读报告；git 仅保留为可选导出（diff 的是报告/snapshot JSON，不是库）。顺带消掉 Windows 长路径 + spawn worktree 的坑。

**2. "被审方接受 → decision"是 F3 的后门**：11.4 写"经用户**或被审方**接受"，若 writer agent（LLM）接受 reviewer 的错误 claim 即成 confidence 1.0 的 decision，回声室经由 acceptance 合法制造事实。改：INV6 补一句"accepted 仅指 role=user"；agent 接受上限为 observation 0.85。

**3. daemon 不可用时 shim 行为未定义**：补 fail-open（降级为无记忆继续工作 + 写 event）+ 懒启动 + 空闲退出。否则 Q6 的"多一个崩溃点"和 G5 的"始终可用"同时不成立——这是几行代码的事，但要写进 INV。

**4. 状态术语混乱**：status=active 但 `valid_to` 已写的条目，逻辑上到底算不算有效？召回过滤条件（`active AND (valid_to IS NULL OR ...)`）、仲裁后输家的终态（archived？rejected？`valid_to` 收紧？）都没定义，否则 12.2 里"暗红=archived"的视觉语义和引擎对不上。

**5. 召回日志要从 16.1 的事后提醒升为 P0 验收指标**：没有日志和反馈信号（pin/forget/"这条没用"），P1 的所有阈值调参都是盲调。同时砍掉突触扩散因子（0.06 权重是噪音，是为可视化美观反向侵蚀检索设计）。

【我不同意你的事实判断】

1. **9.6 / Q4 的论据"直接写库会读到半成品"在你自己的架构里不成立**（已核查 ✅）。INV1 规定所有写入经 daemon、daemon 是唯一写者；SQLite WAL 下读者获得一致性快照，未提交的整合对读者不可见（[sqlite.org/isolation](https://www.sqlite.org/isolation.html)）。worktree+diff 是 Letta Context Repositories 的做法（你自引的【A】），那边记忆是 git 里的**文本文件**、读者直接读工作区、没有快照隔离，条件不同（[Letta changelog](https://docs.letta.com/reference/changelog)）；你的存储是 SQLite 单文件，"diff"的对象根本不存在——二进制库的 git diff 不可读。
2. （温和）**3.2 的"字节稳定 → 复用 prompt cache"被当普适优点**（已核查 ✅ 成立此保留意见）。cache 命中要求 cache_control 块之前的全部内容逐字节一致，稳定内容须位于前缀、动态内容放后（[Claude Platform Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。P4 接多宿主时 hook 时机不同（SessionStart vs UserPromptSubmit）、各宿主拼装顺序不同，cache 命中不会自动获得，adapter.config 里需要显式约束注入点顺序，建议在 10.5 的表里加一行。

【被低估的风险】

**信任静默衰减**。坏注入一两回（stale 事实与当下现实冲突），用户就把整个记忆块当噪音——但每轮 ~2k token 的注入成本照付，且 G2（有界）、G3（可解释）全部照常绿灯，**没有任何指标度量"用户已不再相信注入内容"**。系统在所有验收指标通过的同时悄然归零。对策：把"这条没用/错了"的一键反馈做进注入点本身（而非可视化里），把注入信任度作为健康指标进 `status` 工具与睡眠报告——反馈闭环在注入现场，不在星图里。
